# 发送门禁系统性审查与修改方案

**审查日期**：2026-06-26  
**审查对象**：`send_email.py`、`report_pipeline.py`（去重与门禁模块）、`settings.py`  
**触发原因**：用户修复报告后重新生成并尝试发送，被三重门禁阻止，暴露数据路径不一致与门禁逻辑过严问题。

---

## 1. 执行摘要

本次审查发现 **3 个根因级问题**，共导致 5 个具体错误：

| 问题编号 | 问题名称 | 严重程度 | 影响 |
|---------|---------|---------|------|
| P1 | 日期级门禁与帖子级去重理念冲突 | 🔴 高 | 阻止了修复后重发的合理场景 |
| P2 | 数据目录不一致导致读取旧 approved | 🔴 高 | 脚本读取凌晨旧数据（2条），而非新数据 |
| P3 | 修复后重发的增量更新逻辑缺失 | 🟡 中 | 无法区分"已发送的旧URL"和"新URL" |

---

## 2. 根因分析

### P1：日期级门禁过严，与"帖子实际发送时间"规则冲突

**现状**：
```python
# send_email.py:266-280

def has_successful_send_for_date(date_str) -> bool:
    # 检查 send_log.json
    if any(entry.get("date") == date_str and entry.get("status") == "success" ...):
        return True
    # 检查 history_index.json
    return any(entry.get("first_sent_date") == date_str for entry in history.get("entries", []))
```

**问题**：
- 该函数在**日报级别**阻止发送：只要 `2026-06-26` 有成功记录，任何后续发送都被阻止。
- 但 `history_index.json` 的 `first_sent_date` 字段本意是**帖子级别**的去重——记录"这个帖子首次被发送的日期"。
- 两者混用导致：即使新报告中包含全新 URL（从未发送过），也因为"日期已发送"而被整体阻止。
- 这与用户要求的"不基于索引，而是基于帖子实际发送时间"的理念直接冲突——**日期级阻止本质上就是基于日期索引，而非帖子级去重**。

**实际表现**：
```
[发送门禁] 日期 2026-06-26 已发送过日报，禁止重复发送
```

---

### P2：数据目录不一致，脚本读取旧数据

**现状**：
```python
# settings.py:17-22
PROJECT_ROOT = Path(
    os.getenv("SYNBIO_DAILY_HOME", Path(__file__).resolve().parents[1])
).resolve()
DATA_DIR = PROJECT_ROOT / "data"
```

**问题**：
- 当从 `github-repo\synbio-daily-agent\scripts\` 运行脚本时，`PROJECT_ROOT` 自动指向 `github-repo\synbio-daily-agent\`，因此 `DATA_DIR` 指向 `github-repo\synbio-daily-agent\data\`。
- 用户手动生成的新报告保存在外层目录 `D:\AI\合成生物行业报告\`，但脚本没有读取外层 `data\` 目录。
- 脚本读取的是 `github-repo\synbio-daily-agent\data\approved_2026-06-26.json`，该文件是**凌晨 02:31 生成的旧数据**（仅 2 条：华熙生物、华恒生物）。
- 这两条旧数据的 URL 已经在 `history_index.json` 中标记为 `first_sent_date: 2026-06-26`。
- **结果**：日期门禁失败（日期已发送）+ URL 去重失败（2 条旧 URL 已发送），双重错误。

**关键证据**：
```
✅ approved数据已保存: 2 条信息   ← 脚本读取的是凌晨旧数据
⚠️ 搜索日志提示: 以下搜索轮次执行过但未产生raw候选: llm_dynamic, r1b, r6
```

### P3：修复后重发的增量更新逻辑缺失

**现状**：
```python
# send_email.py:383-400
sent_url_check = validate_approved_not_previously_sent(approved_data, ...)
if not sent_url_check["is_valid"]:
    if force_send: ...
    elif not enforce_send_once: ...
    else:
        errors.extend([f"[URL去重] {error}" for error in sent_url_check["errors"]])
```

**问题**：
- `validate_approved_not_previously_sent` 是**全有或全无**的阻断：只要 approved 中有任何 URL 已发送过，就生成 error 阻止整个发送。
- 合理的修复后重发场景：用户修改了报告，approved 中包含 3 条旧 URL（已发送）+ 5 条新 URL（未发送）。
- 当前逻辑：整体阻止，要求用户全部用新 URL 或全部用 `--force-send`。
- 期望逻辑：过滤掉已发送的旧 URL，仅发送新 URL；如果过滤后 approved 为空，再阻止。

**与"基于帖子实际发送时间"规则的关系**：
- URL 去重检查本身**已经实现了**基于帖子实际发送时间的规则（`first_sent_date` 记录每个帖子的首次发送日期）。
- 但**日期级门禁**（`has_successful_send_for_date`）和**全有或全无的阻断策略**破坏了这个好设计。

## 3. 错误影响评估

### 对本次 6-26 日报的影响

| 检查项 | 脚本读取的旧数据 | 用户新生成的实际数据 | 差异 |
|-------|---------------|------------------|------|
| approved 数量 | 2 条 | ~15+ 条（重新搜索后） | 严重偏差 |
| 头条新鲜度 | 5-6 天前（华熙生物、华恒生物） | 1-2 天前（证监会政策、华宝股份） | 严重偏差 |
| 政策板块 | 缺失 | 证监会科创板、武汉研发计划、NSFC 指南 | 严重缺失 |
| 融资板块 | 缺失 | NewLimit $435M、Pumpkinseed $20M 等 | 严重缺失 |
| 学术活动 | 缺失 | SEED 2026、BIO 2026、亚洲六国路线图 | 严重缺失 |

**结论**：由于数据路径不一致，脚本实际上是在尝试"重发凌晨的旧报告"，而非发送用户修复后的新报告。门禁正确地阻止了这种无意义的重发，但用户本意的"发送新报告"被连带阻止。

## 4. 修改方案

### 4.1 修改一：日期级门禁降级为 warning（核心修改）

**目标**：移除"基于日期的整日报阻止"，完全依赖"基于帖子实际发送时间"的 URL 级去重。

**文件**：`send_email.py`

**修改前**：
```python
# send_email.py:352-359
if has_successful_send_for_date(date_str):
    duplicate_message = f"[发送门禁] 日期 {date_str} 已发送过日报，禁止重复发送"
    if force_send:
        warnings.append(...)
    elif not enforce_send_once:
        warnings.append(...)
    else:
        errors.append(duplicate_message)
```

**修改后**：
```python
# 日期级门禁降级为 warning，不再阻断发送
# 真正的去重由 validate_approved_not_previously_sent（URL级）负责
if has_successful_send_for_date(date_str):
    duplicate_message = f"[日期提醒] 日期 {date_str} 已有发送记录"
    warnings.append(duplicate_message)
    # 仅在 approved 全部为空且日期已发送时才阻断（见修改二）
```

**理由**：
- "一天不允许发两次"是用户的要求，但用户的意思是"不要把同样的内容发两次"。
- URL 级去重已经精确实现了这一点——已发送的帖子不会重复发送。
- 日期级门禁阻止了"修复后发送新内容"的合理场景，是过度防御。

---

### 4.2 修改二：增量更新发送——过滤已发送的旧 URL

**目标**：允许同一天发送新 URL，只过滤已发送的旧 URL。

**文件**：`send_email.py` 或 `report_pipeline.py`

**修改前**：
```python
# send_email.py:383-400
sent_url_check = validate_approved_not_previously_sent(...)
if not sent_url_check["is_valid"]:
    if force_send: ...
    elif not enforce_send_once: ...
    else:
        errors.extend(...)  # 全有或全无阻断
```

**修改后**：
```python
# 新增：增量过滤逻辑
sent_url_check = validate_approved_not_previously_sent(...)
if not sent_url_check["is_valid"]:
    # 获取已发送的 URL 索引
    sent_indices = {e["index"] for e in sent_url_check.get("checked", []) 
                     if e.get("dedup_key") in sent_url_check.get("sent_keys", {})}
    
    # 过滤已发送的 approved 项
    new_approved = [item for i, item in enumerate(approved_data, 1) 
                    if i not in sent_indices]
    
    if len(new_approved) == 0:
        errors.append(f"[发送门禁] 所有 approved URL 均已发送过，日期 {date_str}")
    else:
        approved_data = new_approved
        warnings.append(f"[URL去重] 已过滤 {len(sent_indices)} 条已发送信息，剩余 {len(new_approved)} 条新信息待发送")
```

**注意**：需要同步修改 `validate_approved_not_previously_sent` 返回结构，使其包含 `sent_keys` 映射，便于过滤。

### 4.3 修改三：数据路径一致性检测与警告

**目标**：防止脚本读取旧数据而不自知。

**文件**：`send_email.py`

**修改后（新增于 `send_daily_report` 开头）**：

```python
expected_approved = DATA_DIR / f"approved_{date_str}.json"

```

**更彻底的方案**：
- 修改 `settings.py`，增加 `OUTER_DATA_DIR` 备用路径
- 在 `send_email.py` 的 `main()` 中增加 `--data-dir` 参数，允许显式指定数据目录
- 或者：规定所有操作必须通过 `SYNBIO_DAILY_HOME` 环境变量指定外层目录，禁止依赖脚本自动推导的 `PROJECT_ROOT`

**目标**：完善"基于帖子实际发送时间"的审计追踪。

**文件**：`send_email.py` 中的 `_update_history_index`

### 4.5 修改五：修复 `has_successful_send_for_date` 的冗余检查

**现状**：该函数检查两个来源：
1. `send_log.json` 中 `date == date_str` 且 `status == success`
2. `history_index.json` 中 `first_sent_date == date_str`

**问题**：这两个检查是冗余的。`send_log.json` 记录的是"日报发送行为"，`history_index.json` 记录的是"帖子发送行为"。当日报发送成功时，两者应该同步更新。

**修改建议**：保留 `send_log.json` 检查（用于审计），但将其从 `has_successful_send_for_date` 中移除，改为单独的检查函数 `has_date_send_record` 仅用于日志审计。门禁去重只依赖 `history_index.json`（帖子级）。

```python
def has_date_send_record(date_str: str) -> bool:
    """仅用于审计，不用于门禁阻断。"""
    log = _load_send_log()
    return any(entry.get("date") == date_str and entry.get("status") == "success" 
               for entry in log.get("sends", []))
```

## 6. 验证方案

修改后，需要验证以下场景：

### 场景 A：首次发送（正常流程）
- 新日期，approved 全部是新的 URL
- **预期**：通过所有门禁，发送成功，history_index 记录 first_sent_date

### 场景 B：修复后重发（本次触发的场景）
- 同一天，approved 包含 3 条旧 URL（已发送）+ 5 条新 URL
- **预期**：日期门禁 warning（不阻断），旧 URL 被过滤，新 URL 成功发送，history_index 更新 last_sent_date

### 场景 C：完全重复发送（应该阻止）
- 同一天，approved 全部是已发送过的旧 URL
- **预期**：所有 URL 被过滤，approved 为空，发送被阻断并提示"所有 URL 均已发送"

### 场景 D：数据路径不一致
- 运行脚本时仓库 data 目录缺少当天 approved，但外层目录存在
- **预期**：预检查发出 warning，提示用户同步数据

## 8. 结论

当前系统的 **URL 级去重（`validate_approved_not_previously_sent` + `history_index.json`）已经正确实现了"基于帖子实际发送时间"的去重规则**。问题出在：

1. **日期级门禁（`has_successful_send_for_date`）与这一理念冲突**——它基于日期索引阻止整日报，而非基于帖子级去重。
2. **数据路径不一致导致脚本读取旧数据**——`send_email.py` 读取的是仓库内凌晨生成的旧 approved，而非外层目录用户修复后的新数据。
3. **缺少增量更新逻辑**——无法区分"已发送的旧帖子"和"新帖子"，只能全有或全无地阻断。

建议按 P0 → P1 → P2 的顺序实施修改，其中 P0 的修改（日期门禁降级 + 增量过滤）可以立即解除当前阻塞，让用户能够发送修复后的新报告。
