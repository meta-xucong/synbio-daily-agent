## 二、根因分析（5 个系统性问题）

### 问题 1：搜索引擎日期不可信（最严重）

搜索引擎返回的 `date` 字段是**索引/收录/转载日期**，不是原始页面的**实际发布日期**。

- 36kr 文章：搜索引擎标注 "2026-06-21"，但实际原文是 "2024年11月22日，方昕博士做客科大硅谷大讲堂"
- 曾安平院士：搜索引擎标注 "2026-06-17"，但实际原文是 "2026年3月28日，绿碳科学发展研讨会"
- 深圳立法：搜索引擎标注 "2026-06-24"，但实际原文是 "2025年8月29日，经深圳市第七届人民代表大会常务委员会第四十次会议审议通过"

**根因**：系统直接采信搜索引擎返回的日期，未对原始页面做二次验证。

### 问题 2：去重逻辑失效

同一 URL `36kr.com/p/3051114996943496` 在 **6-24 和 6-25 连续两天** 都出现在邮件中。

**根因**：去重以**标题指纹**为主要匹配依据，但 6-25 的标题被改写为"方昕博士解读生物制造产业落地：四城市政策对比"，与 6-24 的标题"从实验室到应用场！方昕博士解读生物制造产业落地与投资逻辑"不同，导致指纹匹配失败。系统没有以 **URL** 作为兜底去重键。

### 问题 3：死链未预检

`http://www.sz.gov.cn/cn/xxgk/zfxxgj/yjzj/content/post_11478950.html` 在发送前返回 **404**，但直接写入了邮件。

**根因**：发送流程中没有对邮件内所有链接做 HTTP 有效性检查。

### 问题 4：内容类型未区分

市场研究报告（如 IIM 的 "2026-2030 年全球合成生物学产品行业发展趋势研究报告"、Polaris 的 "Synthetic Biology Market Analysis Report 2026-2034"）被分类为"新闻"，与当日新闻并列发送。

这些报告的特点是：
- 发布日期可能是新的（2026-06-19），但内容主体是**历史数据回顾**（2024年融资、2025年市场规模）
- 属于**行业分析**，不是**事件报道**

**根因**：系统没有区分"新闻报道"（新事件）和"市场研究报告"（历史数据汇总）。

### 问题 5：时效性窗口执行不严格

- 政策文件：2026-04-16 印发的文件，在 6-24（两个月后）被当作"新发布"发送
- 研究论文：2026-06-12 发表的论文，在 6-21（9 天后）发送尚可，但系统未对"论文 vs 新闻"设置不同窗口

**根因**：不同内容类型应有不同的时效性窗口，但系统没有分类设槛。

## 三、修复方案（代码层面）

### 修复 1：原始页面日期验证（fetch 验证层）

**目标**：解决"搜索引擎日期不可信"问题。

**方案**：在搜索结果进入候选池后、发送门禁前，增加一层 `fetch_date_verification`：

```python
async def fetch_and_verify_date(url: str, search_date: str) -> dict:
    """
    对候选条目 fetch 原始页面，提取真实发布日期。
    返回：{"verified_date": str, "confidence": str, "source": str}
    """
    try:
        response = await fetch_url(url, timeout=10)
        html = response.text
        
        # 1. 从 HTML meta 标签提取日期（优先级从高到低）
        dates = []
        
        # 高优先级：结构化数据
        dates.extend(extract_meta_dates(html, [
            "article:published_time",      # Open Graph
            "datePublished",               # Schema.org
            "publishdate",                 # 常见中文站
            "published_time",
            "og:updated_time",
            "dateModified",
        ]))
        
        # 中优先级：正文正则匹配（中文/英文日期格式）
        dates.extend(extract_body_dates(html, [
            r"(\d{4})\s*年\s*(\d{1,2})\s*月\s*(\d{1,2})\s*日",  # 2024年11月22日
            r"(\d{4}-\d{2}-\d{2})",                                # 2024-11-22
            r"Published\s+on\s+(\w+\s+\d{1,2},\s*\d{4})",         # Published on November 22, 2024
        ]))
        
        # 2. 交叉验证：取 meta 日期和正文日期的最早值（最保守策略）
        if dates:
            verified_date = min(dates)  # 最早的日期 = 最可能的原始发布日期
            confidence = "high" if len(dates) >= 2 else "medium"
        else:
            verified_date = search_date
            confidence = "low"
            
        return {
            "verified_date": verified_date,
            "confidence": confidence,
            "source": "meta" if dates else "search_fallback"
        }
    except Exception:
        return {
            "verified_date": search_date,
            "confidence": "low",
            "source": "search_fallback"
        }
```

**门禁规则**：
- `confidence == "high"`：以 `verified_date` 为准参与时效性判断
- `confidence == "low"`：以 `search_date` 为准，但**降低评分权重**（如 AI 评分 -20 分）

### 修复 2：URL 级永久去重

**目标**：解决"同一文章连续多天发送"问题。

**方案**：建立**全局已发送 URL 数据库**（`data/sent_url_registry.json`），以 URL 去重键为唯一索引。

```python
URL_DEDUP_KEY_RULES = {
    # 去掉查询参数和锚点，保留域名+路径
    "default": lambda url: urlparse(url)._replace(query="", fragment="").geturl(),
    # 对微信文章特殊处理：biz+mid 为唯一标识
    "weixin": lambda url: extract_weixin_id(url),
    # 对 36kr 特殊处理：文章 ID 为路径最后一段
    "36kr": lambda url: re.search(r"/p/(\d+)", url).group(1),
}

def get_dedup_key(url: str) -> str:
    """生成 URL 去重键"""
    domain = urlparse(url).netloc.lower()
    
    if "mp.weixin.qq.com" in domain:
        return URL_DEDUP_KEY_RULES["weixin"](url)
    elif "36kr.com" in domain:
        return URL_DEDUP_KEY_RULES["36kr"](url)
    else:
        return URL_DEDUP_KEY_RULES["default"](url)

# 在 approved_llm.json 生成前、邮件发送前，各检查一次
if get_dedup_key(url) in sent_url_registry:
    reject_reason = f"[去重] URL 已发送过: {get_dedup_key(url)}"
    action = "排除"
```

**数据持久化**：
```json
// data/sent_url_registry.json
{
  "registry": {
    "36kr.com/p/3051114996943496": {
      "first_sent_date": "2026-06-24",
      "title": "从实验室到应用场！方昕博士解读...",
      "sent_count": 2
    }
  }
}
```

**注意**：URL 去重与标题指纹去重**并行执行**，任一匹配即排除。URL 去重是**永久性**的（一旦发送过，永不再次收录），标题指纹去重是**周期性**的（如 30 天内）。

### 修复 3：发送前死链预检

**目标**：解决"404 链接流入邮件"问题。

**方案**：在邮件 HTML 生成后、发送前，增加 `pre_send_link_check` 步骤：

```python
async def pre_send_link_check(html_content: str) -> tuple[str, list]:
    """
    对邮件中所有 <a href="..."> 链接执行 HEAD 请求。
    返回：修正后的 HTML、死链列表
    """
    soup = BeautifulSoup(html_content, "html.parser")
    dead_links = []
    
    for a_tag in soup.find_all("a", href=True):
        url = a_tag["href"]
        if not url.startswith("http"):
            continue
            
        try:
            async with aiohttp.ClientSession() as session:
                async with session.head(url, timeout=10, allow_redirects=True) as resp:
                    if resp.status >= 400:
                        dead_links.append({
                            "url": url,
                            "status": resp.status,
                            "context": a_tag.get_text(strip=True)[:50]
                        })
                        # 标记为死链（红色样式）
                        a_tag["style"] = "color: #cc0000; text-decoration: line-through;"
                        a_tag["title"] = f"链接无法访问 (HTTP {resp.status})"
        except Exception as e:
            dead_links.append({"url": url, "status": "timeout/error", "error": str(e)})
    
    # 如果死链数量 > 0，写入日志并通知
    if dead_links:
        await log_dead_links(dead_links)
    
    return str(soup), dead_links
```

**更严格的方案（推荐）**：如果某条信息的**唯一链接**是死链，则**整条信息从邮件中移除**，而不是保留带删除线的链接。这适用于链接是信息唯一来源的情况。

### 修复 4：内容类型分类与分栏

### 修复 5：分类时效性窗口

**目标**：解决"两个月前的政策文件被当作新发布"问题。

**方案**：根据 `content_type` 应用不同的时效性窗口：

```python
TIMELINESS_WINDOWS = {
    "news": 3,      # 新闻：3 天
    "policy": 7,    # 政策：7 天（从文件印发日期或报道发布日期起算）
    "research": 14, # 论文：14 天
    "report": 30,   # 报告：30 天
    "event_preview": 60,  # 活动预告：60 天
}

def check_timeliness(item: dict, report_date: str) -> bool:
    """
    检查条目是否在时效性窗口内。
    使用 verified_date（原始页面日期）而非 search_date。
    """
    content_type = item.get("content_type", "news")
    window = TIMELINESS_WINDOWS.get(content_type, 3)
    
    # 使用验证后的日期
    item_date = item.get("verified_date") or item.get("date")
    
    days_diff = (datetime.strptime(report_date, "%Y-%m-%d") - 
                 datetime.strptime(item_date, "%Y-%m-%d")).days
    
    return days_diff <= window
```

**特殊规则**：
- 重大突发（如华恒生物实控人刑拘）：绕过时效性窗口，直接通过
- 政策文件：如果"文件印发日期"和"报道发布日期"都超过 7 天，但文件本身非常重要（如全国首部立法），可放入"附录"而非主内容

### 修复 6：日期歧义标注

**目标**：解决"2025年10月1日施行"被误读为旧闻的问题。

**方案**：在 LLM 生成摘要时，增加日期歧义处理指令：

```
在生成摘要时，请注意以下日期类型，不要混淆：
1. "发布/报道日期"：文章/新闻本身的发布日期（如 2026-06-24）
2. "事件日期"：新闻描述的事件发生的日期（如 2026-03-28 的研讨会）
3. "生效日期"：法规/政策未来生效的日期（如 "将于2025年10月1日施行"）
4. "文件印发日期"：政府文件正式印发的日期（如 2026-04-16）

在摘要中，请明确标注：
- 如果是新闻报道："（2026-06-24 发布）"
- 如果是政策文件："（文件印发于 2026-04-16，本报道于 2026-06-24）"
- 如果法规有未来生效日期："（2025年10月1日起施行，2026-06-24 审议通过）"
```

|---|---|---|---|
| **P0** | 修复 1：原始页面日期验证 | 解决最根本的旧闻误发问题 | 中（需集成 fetch 模块） |

| **P2** | 修复 6：日期歧义标注 | 提升阅读体验 | 小（修改 LLM prompt） |

**建议执行顺序**：先做完 P0（3 项），立即解决当前最严重影响用户体验的问题；再依次做 P1、P2。

## 七、备注

1. **fetch 验证可能增加耗时**：每批次候选条目（如 20-30 条）fetch 一次，预计增加 5-15 秒。可考虑异步并发（aiohttp）降低延迟。
2. **URL 去重注册表需要持久化**：建议保存在 `data/sent_url_registry.json`，每次发送后追加写入。
3. **政府网站特殊处理**：`.gov.cn` 域名的页面通常有稳定的 `published_time` meta 标签，fetch 成功率较高。但部分政府网站可能禁止 HEAD 请求（只允许 GET），需要在 `link_checker.py` 中降级处理。
4. **36kr 等站点可能有反爬**：fetch 时需设置合理的 User-Agent，避免被拦截。可考虑使用现有 fetch 工具（如 kimi_fetch_v2 的底层实现）。
